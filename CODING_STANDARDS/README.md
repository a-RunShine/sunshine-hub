# 代码规范

按技术栈分两份：`java.md`、`typescript.md`。

## 给谁看

给 code review 阶段的 reviewer。不是给 implementer 的教程，写代码时不该加载它。

## 三条原则

**规范属于 reviewer**。实现阶段不为它花 token，review 时逐条对照 diff。

**能机器判定的，绝不写进文档**。格式、命名、类型、架构边界、测试，全部进 CI。check 会红，句子不会。

**每条都要挂「谁在强制」**。某个 lint 规则、某个测试，或者显式写「无。这是 review 时的判断题」。挂不上强制手段的规则，要么改成检查，要么删掉。

## 只留判断题

写之前过一遍：这条能写成 lint 规则、类型约束或测试吗？能，就不要写进文档。

剩下的通常是这几类：领域不变式、单一入口、跨文件一致性、「看起来对但其实是错」的设计教训、接口契约要求。

## 规模

每份 5 到 15 条。超过这个数，说明该做成检查的还躺在文档里。

## 关于「为什么」里的例子

本项目代码还没开始写，所以下面每条规则的后果描述来自已知的失败模式，不是这个仓库的历史事故。

第一次真实事故发生后，用它替换对应条目的描述。规则必须能追溯到具体的事，写不出事的规则多半是通用建议，删掉。
