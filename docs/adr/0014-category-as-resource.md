# 商品分类是资源，不是契约里的枚举

分类由后端维护成一份可增删改查的数据，前端读分类列表接口决定显示哪几个。商品存一个分类引用，**OpenAPI 不枚举分类取值**。新增一个分类不需要改契约、不需要重新生成类型、不需要前后端一起发版。

初始五个分类：武器皮肤、角色皮肤、徽章、手办、服饰。一个商品只属于一个分类。

owner 2026-11-19 拍板。触发点是 issue #3 的 P1-1：用户故事要「按分类看商品」，但契约里 `ProductSummary` 只有 `kind`，`GET /products` 只有 `kind` 一个筛选参数，分类没有任何数据来源。落点是 issue #45。

## 分类不是商品形态

这是两个概念，此前只有后者在契约里，且没有正名。

| 概念 | 回答的问题 | 取值 | 谁定 |
|---|---|---|---|
| **Product Kind（商品形态）** | 这东西是虚拟的还是实体的 | `VIRTUAL` / `PHYSICAL`，闭集 | 系统，随履约与运费规则走 |
| **Category（分类）** | 它摆在货架的哪一格 | 开集，运营可增删 | 运营 |

商品形态决定履约方式与运费计算，取值必须是闭集，枚举是对的。分类是货架陈列，会随上架的商品种类变多而增加，枚举是错的。

**拿商品形态当分类用会把皮肤、手办、队服压成两类。** 这不是显示问题：首页的分类筛选会失去意义，而运费与履约规则又反过来被分类污染。两者必须各自独立。

## Considered Options

- **在契约里把分类写成枚举。** 最省事，一张表都不用建，前端可以直接按枚举值硬编码图标与配色。但加一个分类要改 OpenAPI、重新生成类型、前后端一起发版；运营无法自助新增。owner 明确要求「后续添加分类要方便」，这条直接不满足。
- **先枚举、以后需要时再改成资源。** 看似渐进，实则把破坏性变更推到最贵的时候：那时前端已经按枚举值写了图标映射与分支逻辑，契约变更会同时打断前端与既有数据。现在选资源比以后换便宜得多。
- **分类做成资源，但管理端只做新增，改和删后置。** 能少写两个接口。但改名与调顺序是运营最先要用的能力（分类名写错、货架顺序要调），缺了就得回到数据库改数据；owner 选择一起做。
- **多值分类（一个商品挂多个分类）。** 表达力更强，但首页筛选、商品详情展示、运营配置都要处理多归属，且「这个商品到底算哪一类」不再有唯一答案。首版单值够用。

## Consequences

**多一套管理端 CRUD。** 这是选资源必须付的代价，已显式接受。管理端沿用既有约定：创建返 `201` 加完整资源，权限不足返 `403`，更新用 `PUT`，删除用 `DELETE`，不引入 `PATCH`。

**前端不得按分类硬编码图标与配色。** 否则「加分类不改代码」这个收益会被前端抵消——后端加了一条数据，前端仍然要发版才能正确显示它。分类自带名称与排序值，图标用统一样式。这条是资源方案成立的前提，不是风格偏好。

**分类列表接口公开且不分页。** 首页在未登录时也要显示分类，所以不要求登录，与商品列表一致。分类数量是个位数量级，分页只增复杂度，直接返回按排序值升序的数组。

**对外标识用整数 id，与商品一致，不引入 code。** 少一个概念。id 一经分配不变，名称可改；商品引用的是 id，所以改名不影响既有商品的归属。

**删除被引用的分类要拒绝，不做逻辑删除、不做级联改归属。** 分类下仍有商品时返回冲突并提示先迁移商品。逻辑删除会让「这个分类还在不在」到处需要带过滤条件；级联改归属会让商品悄悄跑到别的分类里，两者都让「商品去哪了」难追。

**推荐位不在本决策内。** 它需要独立的运营配置语义（谁被推荐、按什么排序、推荐位有几个），与分类不是一件事，另开一票。

**契约缺口，本轮不改。** 本 ADR 只记决策与约束。分类资源、商品上的分类引用、`GET /products` 的分类筛选参数都由 issue #45 落地；本 ADR 合并时契约里还没有分类。
