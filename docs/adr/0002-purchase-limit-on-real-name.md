# 限购绑在实名主体上，不绑账号

> **2026-11-16 部分取代，原文保留。**
> 主结论「绑实名不绑账号」**继续有效**。
> Consequences 第二条「限购键挂 `productId`、额度按商品跨场累计、首发抢过的人回流场不该再有资格」被 [ADR-0012](0012-per-campaign-purchase-limit.md) 取代：额度改为按 `campaignId` 挂、每场独立、运营可配 2 件以上。
> 第 5 行的代价**部分失效，不是整段消失**：随 [ADR-0013](0013-two-tier-cooldown.md) 取消永久失格，「真实业务需要客服申诉通道」不再必需——惩罚改成两档可逆冷却，到期自动恢复，不需要人工解封入口。但**共用一张证件的合法用户被误伤这件事仍然发生**，只是后果从不可逆变成有界（最多 7 天）；**存实名指纹的成本一点没少**；「只在错误提示里说清楚是按什么判定的」继续有效。第 5 行原文保留，失效的只有申诉通道那半句。
> 注意 ADR-0012 与本 ADR 的相容处：回流按 ADR-0003 仍在同一场 Campaign 内释放，所以回流不产生新额度。

"一人一单"认的是人，不是账号。同一个人名下的所有账号共享一份额度。账号维度的限购对黄牛没用，注册小号的成本接近于零。

代价是系统要存实名指纹，而且一家人共用一张证件的合法用户会被拦下来。真实业务需要客服申诉通道，本项目不做，只在错误提示里说清楚是按什么判定的。

## Considered Options

- **账号维度**：最好写，但挡不住黄牛，被问"小号怎么防"的时候也答不上来。
- **实名 + 账号 + IP 三重校验**：风控最严，但三条规则缠在一起之后，用户被拦了都不知道该怪哪一条。IP 这一维在真实业务里误伤率很高，同一个公司出口、同一个校园网，一拦一大片。留作后续演进，不进首版。

## Consequences

实名指纹是限购 Redis 键的组成部分，跨账号的限购状态天然共享。

限购键挂 `productId` 而不是 `campaignId`。同一件商品会先后参加多场 Campaign，首发、回流、后来的折扣，额度按商品累计。首发抢过的人，回流场不该再有资格。
