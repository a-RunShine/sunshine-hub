# 实施路径

全部页面先跑起来，后端再按同一份契约实现。这个顺序成立的前提只有一个：契约先定死。

## 前置：两个缺口

这两件事不定，前端第一个页面就写不了。

**管理端形态**。运营要建商品、配规格、建 Campaign、分配配额、发货、审核退款、发公告和活动。做成同一个 SPA 里的 `/admin` 路由，薄 UI，只做四块，不单独建后台项目。

**登录与实名**。账号密码加 JWT。注册时一次填完：用户名、密码、实名姓名、证件号（只存 hash）、大区。不做第三方登录，不做短信验证码。

大区必须在注册时定，因为配额按大区切分，限购按实名累计，这两个东西在第一次抢购之前就得存在。

---

## 阶段 0 · 契约与骨架

**目标**：让前端和后端可以各自开工，不用等对方。

**产出**

1. `api/openapi.yaml`，覆盖 spec 里那三十个接口，含请求体、响应体、错误码
2. 前端脚手架：Vite + React + TypeScript + Tailwind + shadcn 初始化，路由、Zustand、请求层空壳
3. 后端脚手架：Spring Boot 3.5 + Maven，模块包骨架，ArchUnit 四条规则先写成空跑
4. `docker-compose.yml`：MySQL 8、Redis 7、RocketMQ 5
5. CI：Spotless、Checkstyle、ArchUnit、`tsc --noEmit`、vitest

**完成标准**

- `docker compose up -d` 三个中间件能起，健康检查通过
- `mvn test` 绿，且 ArchUnit 报告里 `Tests run` 不是 0
- `pnpm build` 绿
- OpenAPI 通过 Redocly 校验，无 `$ref` 断链

**为什么 CI 要在这一步建**：等写完代码再补检查，就是补一堆历史欠账。这一步建好，后面每个提交都在被检查。

---

## 阶段 1 · 前端可点

**目标**：全部页面用 Mock 数据跑通主流程，不依赖任何后端代码。

**做法**：MSW 拦截请求，handler 的响应结构严格对齐 OpenAPI。类型从 OpenAPI 生成，不手写。

**页面清单**

| 区域 | 页面 |
|---|---|
| 身份 | 注册（含实名、大区）、登录 |
| 商城 | 首页、商品详情、抢购页 |
| 交易 | 订单列表、订单详情、支付模拟 |
| 资产 | 我的道具库、履约单（发货状态） |
| 售后 | 退款申请、退款进度 |
| 内容 | 公告列表与详情、活动列表与详情 |
| 管理 | 商品与 Campaign 配置、配额分配、发货、退款审核 |

**抢购页单独说**：它是整个项目最复杂的一个页面，倒计时、按钮禁用态、抢购中的转圈、成功后的编号展示、失败的三种原因（已购、售罄、编号池异常）。这个页面先做成能对着人演示的原型，再往下走。

**完成标准**

- 主流程能从头点到尾：注册 → 浏览 → 抢购 → 支付 → 道具库 → 退款
- 关掉网络，页面不白屏，给的是错误态而不是一直转圈
- 每个数据页面都有加载态和空态

---

## 阶段 2 · 后端核心

**目标**：按 OpenAPI 实现全部接口，顺序按依赖排。

**实现顺序**

1. **身份**：账号、实名指纹、大区、JWT
2. **商品**：Product、Sku、Campaign、Allocation 的管理端接口
3. **缓存层**：商品详情的逻辑过期与空值标记
4. **抢购**：Lua 脚本、MQ 异步落库
5. **订单与支付**：状态机、乐观锁、回调幂等
6. **履约**：拆单、发货、签收
7. **退款**：申请、同意、确认收货、回调
8. **延迟任务**：超时关单、回流释放、预约提醒
9. **限流**：AOP 加注解，三维度
10. **内容**：公告、活动

**为什么先打通 1 到 5**：注册、浏览、抢购、下单、支付是一条最短闭环。这条通了，后面履约和退款都是在这条链路上加分支，不会推翻前面的设计。

**完成标准**

- 每个接口在 Swagger 上能调通
- 抢购的并发测试通过：1000 线程抢 100 份，成功数恰好 100
- 限购跨 Campaign 累计生效
- 支付回调幂等：同一 `trade_no` 回调五次，只产生一条记录

---

## 阶段 3 · 联调、压测与收尾

**目标**：把 Mock 换成真后端，拿到可以写进简历的数字。

**产出**

1. 关掉 MSW，修契约差异（差异会有的，这是正常成本）
2. 压测脚本与报告：`wrk` 或 JMeter，注明硬件与并发模型
3. 超卖验证：压测后对账 `available + occupied + pending_repool + sold = total`
4. README：架构图、启动方式、技术决策索引
5. 演示脚本：一条能从注册走到退款的路径

**完成标准**

- 零超卖，且有对账数据支撑
- 抢占接口 P99 在峰值下低于 150ms，或者如实记录实际数字并解释
- 新机器按 README 能在十分钟内跑起来

---

## 依赖关系

```
阶段 0 ──┬──> 阶段 1 ──┐
         └──> 阶段 2 ──┴──> 阶段 3
```

阶段 1 和阶段 2 之间没有依赖，可以并行。唯一的硬依赖是阶段 0 的契约。

跳过阶段 0 直接写前端，结果一定是后端实现完之后前端大面积返工。

---

## 风险

**契约不准导致返工**。缓解办法是 OpenAPI 先过一遍评审，重点看错误码和分页结构，这两处最容易事后改。

**前端先做完发现交互实现不了**。抢购页的成功与失败态是纯前端能表达的，但倒计时的服务端时间校准需要接口配合。所以 OpenAPI 里要给一个服务端时间字段，别用客户端时间。

**后端链路长，中间卡住**。缓解办法是把 1 到 5 当成一个必须打通的最小闭环，6 到 10 都是它的分支。闭环不通不做分支。

**压测环境和开发环境不一致**。压测必须在 `docker-compose` 同一份编排里跑，别用本地直连的 MySQL。
