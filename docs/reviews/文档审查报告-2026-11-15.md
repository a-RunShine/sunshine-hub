## 一句话结论

文档的**方法论水平明显高于内容完备度**。决策记录的质量、术语治理、评审规范的设计思路都在平均线以上，是可以直接当作品集拿出去讲的那一档；但**领域模型有几处会直接导致实现出错的结构性缺口**，尤其是库存的真相源、跨场配额守恒、折扣定价规则这三块，目前按文档写代码一定会踩坑。

# 一、优点

## 文档架构

**1. spec 与 ADR 的职责切得很干净。**
spec 讲"做什么、怎么落"，ADR 只讲"为什么这么选、否掉了什么"。7 篇 ADR 里 6 篇都有 `Considered Options`，且被否掉的方案都给了具体的否掉理由（不是"不够优雅"），这是 ADR 的正确用法，不是流水账式决策日志。

**2. 术语表带反向清单。**
`GLOSSARY.md` 每条都写了 `_Avoid_:`，明确排除同义词。多数项目的术语表只做"正名"，不做"禁名"，而后者才是防漂移的关键。配合 `docs/agents/domain.md` 里"输出里出现领域概念时用表里的词"，形成了一条闭环约束。

**3. 文档分层与加载策略有 token 意识。**
`AGENTS.md` 只做索引和一页纸摘要，细节下沉到 `docs/agents/*.md`；`CODING_STANDARDS/README.md` 明写"给 reviewer，不给 implementer 加载，实现阶段不为它花 token"。这是把"上下文成本"当设计约束在考虑，少见。

**4. spec 在 Issue 里做单向镜像。**
Issue #2 顶部标明"规格源文件：docs/specs/0001…"，正文是本地文件的镜像（图片链接换成 raw URL 适配渲染）。我逐字 diff 过，除图片链接外**完全一致**。单向镜像避免了双向漂移，比"两边都能改"健康得多。

**5. 提交历史与决策同步演进。**
9 个提交，一步一个决策：从"发售系统"扩到"商城"、Java 21 切 25、退款纳入范围、规范按技术栈拆两份。每条 commit message 都能对应到文档的一次实质性变更，可追溯性完整。

## 决策质量

**6. 每个反直觉的决定都给了"反过来会怎样"。**
- 限购键挂 `productId` 不挂 `campaignId`：因为额度属于商品，跨场累计。
- 编号不回收：回收重发会出现两个用户拿同一张截图。
- 回流延迟 30 分钟：立刻回，黄牛能零成本探测真实库存。
- 虚拟商品不计入包邮门槛：99 块皮肤会把 5 块徽章带成包邮，运费规则白设。

这四条的共同点是**都从攻击者视角或边界场景倒推**，不是从代码整洁度倒推。这是文档里最值钱的部分。

**7. "不做"写得比"做"清楚。**
范围外 7 条，每条带理由。尤其是"签收不做自动超时确认——那需要一套定时任务和争议处理，不属于本项目"，明确划了能力边界而不是含糊带过。

**8. 承认不一致，并且论证它。**
"两条下单路径并存是刻意的…强行统一只会两边都不讨好"。多数文档遇到这种不一致会藏起来或者强行抽象，这里选择显式辩护，可读性和可信度都更高。

**9. 三条延迟链路共用一个通道的理由说得住。**
"三种语义完全不同的延迟任务跑一条通道，比'我用延迟队列做了关单'耐问得多"——这句背后的判断是对的：技术选型的说服力来自覆盖场景的宽度，不是单点的精巧。

## 评审规范

**10. "能机器判定的绝不写进文档"这条元规则很硬。**
配套三条：规范属于 reviewer、每条挂"谁在强制"、超过 15 条说明该做成检查的还躺在文档里。这把文档从"规范全集"降级成"判断题库"，是正确的位置。实际条数也守住了（Java 10 条、TS 9 条）。

**11. 用"删除测试"作为深度的判据。**
"想象把这个类删掉，逻辑只是搬回调用方、调用方各加两行，那它是转发器"。给了四个可操作的信号（Controller 注入 Repository、Service 方法只有一行、十个不相干的 public 方法、包外 import `internal`），比"高内聚低耦合"这类口号有用得多。

**12. 规范里的例子诚实标注了来源。**
"本项目尚未有真实事故，括号内的场景来自同类项目的常见失败"。没有伪造事故履历，也留了替换机制（第一次真实事故后用它替换描述）。这种自我标注在 AI 生成文档泛滥的当下格外重要。

**13. 测试决策有"唯一能证明某事"的自觉。**
"这是唯一能证明'没有超卖'的测试，必须进 CI"，并且点名三件事必须同时断言（配额归零、Unit 数等于成功数、编号不重复），还解释了少一条为什么不够。这是真跑过并发测试的人才写得出的。

# 二、缺点

按后果严重度分四层。P0 是"照文档写必然出错"，P1 是"agent 无法独立完成"，P2 是"能写出来但会踩坑"，P3 是"影响长期维护"。

## P0 · 领域模型的结构性缺口

### P0-1 库存有三个真相源，彼此没有换算关系

`t_sku.stock`（常规）、`t_allocation.total`（抢购）、`t_product.total_limit`（总量）三份库存并存，但文档没有定义：

- 一个 Campaign 开抢前，`allocation.total` 是否从 `sku.stock` 里预扣？
- 同一个 Sku 同时挂在一场 FLASH 和一场 NORMAL（时间窗重叠）时会怎样？
- 三方数量对不上时，以谁为准？

现状是两个路径各扣各的字段，**没有任何约束禁止同一 Sku 双路径并发售卖**。这不是理论风险：运营给一个手办同时配"常驻售卖 + 限时折扣"，就是标准的双卖场景。

> 位置：spec 第 124–147 行（表结构）、第 228–236 行（两条下单路径）

**建议**：明确"Allocation 是 Sku 库存在抢购场的切片，切出去的部分从 sku.stock 扣减"，并加一条 DB 约束或应用层校验：同一 `sku_id` 的在售 Campaign 时间窗不得重叠。

### P0-2 `total_limit` 只做单场校验，跨场可以卖爆

ADR-0004 允许同一商品先后参加多场 Campaign。spec 说配配额时"校验总和不超过限量"——但这是**单场**内 `Σ allocation.total ≤ product.total_limit`。

首发场分 5000，回流场再分 5000，两场各自都合法，商品实际卖出 10000 件。

> 位置：spec 第 160–166 行（关键约束）、用户故事 35

**建议**：`total_limit` 的守恒要在"商品 × 全部 Campaign"这一层做，需要一个聚合读数（`Σ 各场已分配`）或把总量校验挪到 Campaign 创建时对 `Σ` 做检查。守恒式目前只写在 `t_allocation` 内部四态上（available+occupied+pending_repool+sold=total），漏了跨场这一维。

### P0-3 Redis 是扣减的真相源，但没有重建路径

抢购的可用份数存在 `alloc:stock:*`，编号池存在 `alloc:pool:*`，DB 只是异步跟随。文档对以下全部沉默：

- Redis 重启、主从切换、内存淘汰（没写 `maxmemory-policy`）之后，`stock` 和 `pool` 从哪来？
- 谁负责从 `t_unit` + `t_allocation` 重建？重建期间抢占接口返回什么？
- DB 与 Redis 出现偏差时，谁是对账的基准？

这是整套设计里最大的运维空白。压测能过、功能能跑，但一次 Redis 故障就会让"零超卖"这个核心承诺失去依据。

> 位置：spec 第 176–190 行（Redis 键设计）之后缺一节

**建议**：补"缓存重建与对账"一节：以 DB 为最终真相、Redis 为可重建的投影；活动开始前预热（含校验 `pool` 长度 == `stock`）；提供管理端"重建某场库存"的接口；消费端落库失败时不允许静默。

### P0-4 折扣价怎么算，整篇没有落点

`t_sku.price` 和 `t_campaign.discount_price` 两个字段都在，但没有任何一处说明**直接下单时价格取哪一个**：

- 时间窗内就走 discount_price？靠什么判定？
- 同一商品两场 DISCOUNT 重叠，取低的还是取后创建的？
- 下单后折扣结束，支付时按原价还是下单时价格？（`t_order_item.unit_price` 像是价格快照，但没明说锁价语义）
- `POST /api/orders` 的请求体是否带 `campaignId`？多商品混合下单时每件各自取哪场？

用户故事 15"价格按折扣算"目前**没有任何实现落脚点**。

> 位置：spec 第 348–358 行（接口契约）、第 119–148 行（表结构）

**建议**：补一节"定价规则"：判定优先级（时间窗 → Campaign 类型 → 最低价）、下单即锁价（`unit_price` 快照，支付时不重算）、重叠的确定性规则（按 `created_at` 或显式 `priority` 字段）。

### P0-5 订单状态机缺 `CLOSED → REFUNDED` 这条边

spec 正文明确写"关单先成、支付回调后到时，订单已经 `CLOSED`，钱却收了，必须转自动退款"，但第 293–298 行的状态机图里 **`CLOSED` 是终态、无出边**。

那么自动退款完成后 `order.status` 是什么？留在 `CLOSED`（钱收了又退了，状态看不出来）还是转 `REFUNDED`（但图里没这条边）？

更麻烦的是 ADR-0007 说"只有全额退款才把订单转成 `REFUNDED`"——`CLOSED` 订单的全额退款算不算这条规则？两处规则在这里直接打架。

> 位置：spec 第 291–311 行 vs `docs/adr/0007` 第 14–18 行

**建议**：给 `CLOSED` 加一条 `→ REFUNDED` 的出边并标注触发条件（`SYSTEM_AUTO` 退款成功），或引入 `CLOSED_REFUNDED` 区分"没付钱关单"和"付了钱退回去"。

### P0-6 混合订单永远到不了 `REFUNDED`

ADR-0007 定：虚拟履约单完成即不可退；只有全额退款才转 `REFUNDED`。

混合订单（皮肤 + 手办）里虚拟那张永远退不掉，所以这个订单**在数学上不可能"全额退款"**，永远停在 `PAID`。而 `t_order` 没有 `refunded_amount` 字段，也没有"可退金额"的概念，无法判断"是否已退干净"。

> 位置：`docs/adr/0007`、spec 第 336–338 行

**建议**：把"全额"的定义改成"可退部分已全部退完"，并给 `t_order` 加 `refunded_amount`（或直接以 `Σ t_refund.amount where status=REFUNDED` 判定）。

### P0-7 限购键的生存期语义自相矛盾，"永久失格"无处安放

同一个 `limit:{productId}:{hash}` 键被两套规则同时要求：

- 额度跨 Campaign 累计 → 键必须**长期存在**（否则过期后能再抢一件）；
- "不到 3 次的，最后一次关闭后 24 小时自动恢复" → 键必须**24 小时过期**。

一个键不可能同时是永久和 24 小时。而且"累计 3 次未支付 → 永久失格"这个状态，`limit`（value 是 orderNo）和 `miss`（24h TTL 的计数）都存不下。

附带一个数据结构问题：`miss` 是 `string` 类型，而规则是"**24 小时内**累计 3 次"——`INCR` 只能做固定窗口，做不了滑动窗口，需要 ZSET 存时间戳。

> 位置：spec 第 179–190 行

**建议**：拆成三个键：`rate:{productId}:{hash}`（额度标记，永久，支付成功后写死）、`miss:{productId}:{hash}`（ZSET 或带时间戳的计数，滑动窗口）、`ban:{productId}:{hash}`（失格标记，永久 + 人工解封入口）。

### P0-8 `t_unit` 没有 `owner_account_id`，"我的道具库"查不出来

`t_unit` 只存 `owner_purchaser_hash`。但用户故事 27 和 `GET /api/me/items` 是**按账号**查"我拥有什么"。

后果：同一实名的两个账号会互相看见对方的藏品（因为 purchaser_hash 相同），而 unit 表本身也无法支撑"这个账号有哪些道具"——只能绕回 `t_order_item` join。

> 位置：spec 第 131–132 行、第 367 行

**建议**：`t_unit` 加 `owner_account_id`，与 `owner_purchaser_hash` 并存（前者管展示归属，后者管限购与风控）。

### P0-9 限购唯一索引的表达力上限是"1 件"

`UNIQUE KEY uk_purchase (purchaser_hash, product_id, limit_flag)`，限购商品写 `limit_flag=1` → 同一人同一商品**只能有一行**。

但 `purchase_limit` 是个数字（用户故事 32 让运营可配），GLOSSARY 定义是"最多能拿几件，跨 Campaign 累计"。当 `purchase_limit=2` 时：

- 第一次买 1 件 → 一行 ✓
- 第二次再买 1 件 → 唯一索引直接拒绝，尽管累计才 2 件、**没超限**

这个索引方案能表达的语义只有"只能交易一次"，与字段的数字语义不匹配。顺带一提，注释"这个字段不参与任何业务查询"也不实——判断额度必须查这张表。

> 位置：spec 第 168–174 行

**建议**：允许同一 (人, 商品) 多行，靠 `SUM(quantity) + 行锁/乐观锁` 校验累计额度；唯一索引只保留给"一人一单"的抢购场景（那是另一条独立约束）。

## P1 · 规格缺口（agent 无法独立完成）

### P1-1 `t_product` 没有分类字段，但故事和接口都要分类

用户故事 1"看到分类和推荐商品"、`GET /api/products` "支持分类与分页"，但 `t_product` 没有 `category`，也没有 `t_category` 表，更没有"推荐"相关字段（`recommend` / `sort_weight`）。**故事、接口、表结构三处不一致。**

### P1-2 接口契约缺两个用户故事要的端点

- 用户故事 21"收到货后确认签收" → 只有 admin 的 `/ship`，没有 user 的 sign 接口。
- 用户故事 18"保存收货地址" → 只有 GET/POST，没有编辑、删除、设为默认。`t_address.is_default` 字段存在但无接口改它。

### P1-3 接口契约只有路径，没有字段定义

spec 说"测试全部打在 HTTP 接口层，从接口的输入输出就能看出来"，但契约里没有一份请求/响应 schema。测试要断言返回值时没有权威字段定义可依，这与 Issue #2 上 `ready-for-agent`（"已完整定义，可交给 agent 独立做"）的标签直接冲突。

### P1-4 异步落库与同步查询之间有可见性缺口

抢占接口返回的 `orderNo` 和编号来自内存，落库靠 MQ 消费者（单机并发 ≤20）。用户在 200ms 后打开"我的订单"（`GET /api/orders/{orderNo}`）时消费者可能还没处理完 → **404**。

文档没提"未落库期间的查询兜底"（Redis 暂存订单快照？返回 202？轮询？）。

### P1-5 消息消费幂等没写

`flash-created` 消息在发送端重试或 Broker at-least-once 下会重投。落库靠什么去重？`t_order.order_no` 唯一索引能挡 insert，但 `t_order_item` / `t_unit` 的更新必须在同一事务内一并幂等——文档只写了"回调幂等"，没写"消息消费幂等"。

### P1-6 预约提醒的定时消息不可撤回

Campaign 创建时就投一条指向"开售前 10 分钟"的定时消息。若创建时间距开售不足 10 分钟、或 Campaign 改期/下架，消息已经在 Broker 里了。消费端必须二次校验（场次是否仍有效、当前时间是否在窗口内、预约是否已取消），文档没写这层守卫。

### P1-7 `t_reserve` 无取消标记、无唯一约束

`DELETE /api/campaigns/{id}/reserve` 只能物理删除；且没有 `(campaign_id, account_id)` 唯一索引 → 重复预约插入多行 → 批量查预约用户时查重。取消率统计也做不了。

### P1-8 `POST /api/orders` 与"单商品 Campaign"的模型冲突

`t_campaign.product_id` 是单商品，而混合订单（虚拟+实体）必然涉及两个 Product、只能走 `/api/orders`。一次请求里每件商品各自对应哪场折扣 Campaign，无法表达。

### P1-9 实名指纹的加盐策略没写

限购全靠"跨账号认出同一人"。若用全局固定盐的 SHA256，证件号空间有限（地区+生日可枚举），存在彩虹表反推风险；若用每账号随机盐，就无法跨账号比对。这是个二选一的安全决策，直接决定限购能否被绕过。文档只写"不可逆变换"。

### P1-10 GLOSSARY 缺三个高频概念

`Pending Repool`（守恒式的一项、ADR-0003 的主题）、`Miss`（失格计数）、`Discount Price` 都没进表。而 `domain.md` 要求"输出里出现领域概念时用表里的词"——这三个词一定会出现。

## P2 · 技术细节（能写出来但会踩坑）

### P2-1 Lua 脚本把"键不存在"和"库存为 0"合并了

`redis.call('GET', stockKey)` 返回 false 时 `or '-1'` → `stock < 1` → 返回 `-2 售罄`。

键没预热、名字拼错、或活动被误删，用户看到的都是"售罄"而不是系统异常。这与同一份文档强调"`-3` 编号池异常要告警，不能当售罄咽下去"的态度**自相矛盾**——同样是配置错误，一个告警一个静默。

**改法**：`GET` 前用 `EXISTS` 区分，键缺失返回 `-4 SYS_ERROR`。

### P2-2 支付回调幂等的表述在技术上不成立

spec 第 165 行："`t_payment` 上 `trade_no` 唯一索引，回调幂等靠它兜底。"

但回调到达时 `t_payment` 记录**已存在**（发起支付时创建），唯一索引只在首次 insert 生效，这时要么 insert 失败（说明设计是把回调当 insert），要么走 UPDATE（唯一索引完全不起作用）。真正的幂等要靠 `UPDATE ... WHERE status='PENDING'` 的 CAS。

而文档自己在第 428 行说"幂等不是加个唯一索引那么简单"——**正文和结尾互相打脸**。退款回调同一问题。

### P2-3 回滚脚本会打乱编号顺序

`LPOP` 从队头取（小编号先出），回滚 `RPUSH` 塞回队尾。若编号池按升序排列（决定"先抢的拿小号"这个隐含语义），一次回滚就让顺序错乱。

文档没承诺顺序，但用户对"1 号"有预期。至少该显式写一句"不保证编号与抢占顺序一致"。

### P2-4 Cache-Aside 的读回填竞态没处理

"更新 DB → 删缓存 → 删失败走 MQ 补偿"只解决了"删失败"，没解决"删成功但被旧值回填"：读请求在删之前拿到旧值、在删之后写回缓存 → 旧值驻留到 30 分钟 TTL。这是 Cache-Aside 的经典竞态，延迟双删和逻辑过期都能兜，文档否掉了前者但没提后者也适用在这里。

### P2-5 逻辑过期的重建线程数没有上限

开售瞬间上千个不同 `productId` 同时逻辑过期，就是上千个重建线程。"起一个线程异步重建 + SETNX 抢锁"没有约束池大小。需要独立有界线程池 + 拒绝策略（拒绝后返回旧值继续服务）。

### P2-6 限流注解的示例值会误导实现

`dimensions = {GLOBAL, IP, USER}, limit = 100, windowSeconds = 1` —— `GLOBAL` 维度 100/s 意味着全站每秒只放 100 个请求，对"几十万人同时点"是全量拒绝。且三个维度共用一个 `limit`，无法给 GLOBAL 宽、IP 严。贴进实现会被照抄。

### P2-7 1000 线程打 HTTP 的并发测试在 CI 里会很脆

Tomcat 默认 `maxThreads=200`，1000 并发里 800 个在排队，这恰好会污染"P99 < 150ms"的断言，还可能因连接超时而非业务失败变红。

要么把正确性测试下沉到 Service/Jedis 层（但这与"测试只打接口层"的原则冲突，需要显式豁免），要么单独调压测用的 `server.tomcat.threads.max`。

### P2-8 RocketMQ 5 的 Testcontainers 成本被低估了

需要 nameserver + broker 双容器、`broker.conf` 挂载、`brokerIP1` 注入宿主机 IP（容器内网地址客户端连不上是常见坑）。文档把它和 MySQL/Redis 并列成一句"Testcontainers 拉起来"，实际难度差一个量级。

### P2-9 运费模板单套 vs 多品类实体商品

`t_freight_tpl` 全局单行。手办和 T 恤的重量体积差得多，真实业务按模板绑定。已声明是简化，但用户故事 36 用了"运费模板"这个词，字面暗示可多套。

### P2-10 "运费不退"的论断与主流电商不符

ADR-0007 说"运费是已经发生的成本，真实电商都这么做"。实际主流平台在**整单退货**时通常退运费（或由运费险覆盖）。全额退货让用户承担全部运费，体验上是负分。至少该区分"整单退"和"部分退"。

## P3 · 文档治理（影响长期维护）

### P3-1 spec 状态与 Issue 标签互斥

本地文件第 3 行写"状态：草案"，Issue #2 打的是 `ready-for-agent`（"已完整定义，可以交给 agent 独立做"）。同一份文档两个互斥状态。

### P3-2 AGENTS.md 说 spec 存在 Issues，但源文件在仓库

`AGENTS.md` 第 21 行："Issues 和 spec 都存在 GitHub Issues 里。" 而 Issue #2 自己写"规格源文件：docs/specs/0001…"。`docs/specs/` 这个目录在 AGENTS.md 和 `issue-tracker.md` 里都没出现——agent 按前者的指引只会去 `gh issue view`，读到的是镜像而非源。

### P3-3 ADR 缺三个标准字段

没有 `Status`（Accepted / Proposed / Superseded）、没有 `Date`、没有 `Superseded by`。0001–0007 看起来都是"已采纳"，但无法判断哪条被后续提交推翻了——比如 spec 从"典藏发售"扩成"商城"后，0001 的"限量编号"前提是否还完整成立。

也没有 ADR 模板文件（`docs/adr/template.md`）。

### P3-4 ADR-0003 缺 `Considered Options` 小节

其余 6 篇都有，0003 把否掉的方案混在正文段落里（"为什么不能立刻回…为什么不开一场独立的回流 Campaign…"）。内容都在，但格式不统一——而这套文档的价值恰恰在"否掉了什么"要被一眼看到。

### P3-5 Module labels 规则现在就是矛盾的

`AGENTS.md` 第 31 行："模块划分定下来之前不建这类标签。第一个模块落地时按模块名创建，此后每个 issue 至少带一个。"

但 issue 现在已存在（#2），模块还没落地 → #2 永远缺 module 标签 → 违反"每个 issue 至少带一个"。要么给"模块未定"一个显式例外，要么这条规则现在就该失效。

### P3-6 triage-labels.md 是零增量文档

五行表格左右两列完全同名，全部信息就是"角色 = 标签字符串"。除了"要换命名风格，改右列即可"这句提示，没有任何本仓库特有信息。按 `CODING_STANDARDS/README.md` 自己的标准（"写不出具体后果的规则，删掉"），它该收回 AGENTS.md 一句话。

### P3-7 issue-tracker.md 混入了 wayfinder 的操作手册

第 41–50 行整段是某个 skill 的 map/ticket 流程全文，与"issue 存哪、怎么用 gh"这个主题无关。同类问题：第 23 行 `**PRs as a request surface: no.**` 是开关变量名的直译，中英混排且对读者无意义。

### P3-8 没有 README.md，但规范里引用了它

`CODING_STANDARDS/java.md` 的"不写在这里的东西"表里明写"环境怎么跑起来 → `README.md`、`docker-compose.yml`"，两者都不存在（当前也没代码，可接受，但表格里应该标"待建"而不是指向空气）。

### P3-9 AGENTS.md 没有构建/测试命令

写了技术栈（Maven、Vitest）但没写 `mvn verify` 还是 `mvn test`、前端用 `pnpm` 还是 `npm`。agent 进来得自己猜包管理器。

### P3-10 `Sku` 的大小写

`GLOSSARY.md` 标题、两张模型图、spec 正文全写 `Sku`，而英文缩写应为 `SKU`（表名 `t_sku` 是对的）。术语表是权威文档，这个拼写会被直接复制到类名——`SkuDO` vs `SKUDO` 会成为一次无意义的重构。

### P3-11 "热门商品页"是未定义术语

用户故事 4 用它，`GLOSSARY.md` 没有，`_Avoid_` 也没收。紧随其后的用户故事 2 用的是"商品详情"。同一个东西两个叫法，违反 `docs/agents/domain.md` 的用词约定。

### P3-12 "连续不重复"与"编号不回收"冲突

`GLOSSARY.md` 说 Collectible Number"同一商品内**连续**不重复"，ADR-0001 说未支付关闭后编号作废不回收。作废后编号必有空洞 → **不再连续**。改成"递增不重复"即可。

### P3-13 模型图没画 `Unit`

两张图覆盖 Product / Sku / Campaign / Allocation 和 Order / Fulfillment，但 `Unit`（ADR-0001 的主角、限量发售的核心物件）一张都没有。图与文字的覆盖面不一致。

另：SVG 里箭头用了 `stroke="context-stroke"`，Chrome 105+ 支持，但部分 SVG 渲染器（含某些 Markdown 预览）会退化成黑色或不可见，稳妥起见写死颜色。

### P3-14 spec 末尾混入面试话术

第 426–428 行"面试最容易被追问的四处""想清楚这个，才说明白…"是元信息，不是规格。放在 spec 末尾会让"给 agent 独立做"的输入混入非需求内容，建议挪到 README 或单独的 `docs/design-notes.md`。

### P3-15 三张表缺时间戳

`t_announcement`、`t_event`、`t_address` 没有 `created_at` / `updated_at`，其余表都有。用户故事 31"按时间倒序"对公告尚可用 `published_at` 兜，地址没有创建时间则无法做"最近使用"这类排序，也与其余表规范不一致。

### P3-16 `t_refund.status` 用 `received_at` 代替状态，查询代价被隐藏了

"同一个 `APPROVED` 覆盖两种情况，靠 `received_at` 是否为空区分"——写路径上省了一个状态，但运营后台"待收货退款单"这个列表必须永远带着 `AND received_at IS NULL`，所有统计口径都要记住这条附加条件。文档承认了这个取舍，但没提查询侧的代价。

# 三、最值得先修的 5 件事

按"修了能解锁多少后续工作"排序，不是按字数。

**1. 定清库存真相源（P0-1 / P0-2 / P0-3 合并处理）**
这三条是同一个问题的三个面：三份库存没有换算、跨场没有守恒、Redis 没有重建。不解决，抢购链路的任何实现都是沙上建塔，而且压测过了也不能证明安全。建议单开一份 ADR 讲清楚"库存分层与守恒"。

**2. 补定价规则（P0-4）**
用户故事 15 现在无落点，`POST /api/orders` 的请求体也没定义。这是唯一一处"业务规则完全空白"的地方，而它影响表结构（要不要 price snapshot、要不要 priority 字段）。

**3. 修订单状态机的两条边（P0-5 / P0-6）**
`CLOSED → REFUNDED` 缺失、混合订单到不了 `REFUNDED`。这是最容易在实现时写成"看起来能跑但状态会失真"的地方，也是面试官最爱追的分支。

**4. 重做限购的键与索引（P0-7 / P0-9）**
一个是生存期语义打架，一个是索引表达力只有 1 件。这两条一起决定了"限购"这个核心卖点能不能自圆其说。

**5. 把 P1 的接口缺口一次补齐（P1-1 / P1-2 / P1-3）**
分类字段、签收接口、契约字段定义。补完之后 Issue #2 的 `ready-for-agent` 标签才名副其实。

# 四、一句额外的话

这份文档最值得保留的不是任何一条结论，而是它的**论证方式**：每个决定都写"不这么做会怎样"，每条规则都问"谁来强制"，每个术语都标"不许叫什么"。

缺点是同一套方法用得不彻底——**在模型层，论证方式被结论取代了**。P0 的那些缺口，几乎都是"看起来已经想清楚了"的地方（库存、状态机、限购），恰恰是没写"如果不这样会怎样"的地方。把这个习惯从技术选型推到建模上，这份文档就是完整的一档。
